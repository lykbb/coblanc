# review 诊断、真实批量入口与交付准备

## 本轮完成

新增 diagnostics.py、live_batch.py、reporting.py、asset_inputs.py：按现有工单格式独立运行视觉／人脸／返工／完整质检，批量记录结果与失败阶段；通过资产库读图，统一输入验证，记录模型版本、提示词哈希、数据集版本、阈值、开始／结束时间、阶段耗时与调用计数。公共节点 check、retouch 的参数和返回值没有改变。

默认模式是 mock：忽略输入照片地址，使用内存生成的双人几何示意图及明确的模拟响应。不能用 mock 判断输入照片是否真实合格。显式 live 才使用资产库内容和真实模型入口。

## 可复现的模拟命令

在 wedding-agent/ 执行：

```bash
uv run python -m app.modules.review.diagnostics app/modules/review/examples/diagnostic_entry.json --mode mock --stage check
uv run python -m app.modules.review.diagnostics app/modules/review/examples/diagnostic_entry.json --mode mock --stage vision --image-id img_2
uv run python -m app.modules.review.diagnostics app/modules/review/examples/diagnostic_entry.json --mode mock --stage face --image-id img_2
uv run python -m app.modules.review.diagnostics app/modules/review/examples/diagnostic_entry.json --mode mock --stage retouch
uv run python -m app.modules.review.live_batch app/modules/review/examples/batch_manifest.json --mode mock
```

两个示例样本均是合成登记；示例 URL 不对应实际资产。样本内的双方授权默认 false，不提供虚假授权。mock 可运行，不能直接切 live 使用这些示例。

retouch 必须有整轮 scores，不能通过 --image-id 只截取一张。check、vision、face 可以指定当前候选编号做单张诊断。retouch 只制定方案，不会自行调用生成模块、修改照片或增加框架 retry_count。

## 输入与真实运行

diagnostics 输入为离线包装 `{sample_id, state, consent}`；state 使用已有 WeddingState 字段。批量包装为 `{dataset_version, samples: [包装, ...]}`。这些包装仅供离线工具，不新增工单或 HTTP 字段。

真实运行应由框架提供或者人工整理私有工单 JSON，包含真实资产库 photo_urls、candidates、brief，返工诊断另带 scores 和必要的 user_feedback。当前 API 不新增内部工单导出接口，CLI 不尝试从另一个进程的内存中获取任务。

live 预检要求：

- 双方已授权、evidence_reference 是真实凭据引用；不把授权原件写入报告。
- 对使用视觉／返工模型的诊断，consent.approved_services 包含当前配置的完整 LLM_BASE_URL；服务须由项目负责人实际批准，不能只为绕过预检填写。
- 相关 LLM_API_KEY、LLM_MODEL_VISION／AGENT 已配置；包含返工的批量评测先检查 agent 配置，避免先消费视觉请求后才发现 agent 不可用。--check-only 可仅做质检。
- review 必须已切到真实模式，例如 REAL_MODULES 包含 review；--mode live 不能绕过 settings.fake_for("review")。可由操作人员在已获准的单次命令环境中设置，不需要本模块修改 .env 或公共配置。
- check／face 的真实服务须已接入。当前 provider_metadata.connected=false，因此会明确停止；vision／retouch 可独立运行，但本轮没有执行实际外部调用。
- 每个样本只执行一次诊断／必要的一次返工决策，无应用层重试。批量样本数由输入清单明确决定，运行前应核对规模和预算。

准备妥当后，操作人员显式使用 --mode live。不要未经服务与预算确认把示例命令改成 live。代码预检只能核对填写的声明，不能替代实际授权和服务审批。

## 报告与运行记录

--output 可指定新的 JSON 文件。不覆盖已有文件；新文件权限为 0600。若路径已存在，换新文件名。未指定时输出标准输出；真实报告包含生物识别评分及修改建议，应保留在获准的私有位置，不提交 Git。

批量返回 predictions 列表、总体 summary 和运行时间。succeeded 表示评测执行完成，不表示图片一定合格。失败样本保留 error 与 failed_stage，继续下一个样本；重复 sample_id 在运行前拒绝。

timing 区分：model_invocations（应用层真实模型调用）、simulated_invocations、face_comparisons（应用层人脸比较）、simulated_face_comparisons。request_budget_upper_bound 仅表示模型 SDK 请求预算，**不代表实际收费请求次数，也不包含尚未确定的人脸 SDK 重试**。报告没有图片、base64、原始工单、资产 URL 或密钥；retouch.patch 仍可能包含用户意见，应视为私有内容。

可取出批量报告的 predictions 列表，作为 evaluation 或 regression 的预测输入。先检查 error、元数据与样本覆盖；不要把失败记录视作已完成质检。单独 vision／face 的报告不含完整 check.result，不能直接冒充整轮评测结果。

本轮执行结果：2 个 mock 样本成功，模型实际调用均为 0，每组 4 次模拟人脸比较；第二组按 hands 反馈产生 generate 方案。

## 人脸服务接入交接清单

1. 决定本地特征模型或获准云服务，记录具体版本、许可证／使用条件与分数尺度。
2. 由框架统一新增依赖、settings／.env.example；模块不自行修改公共文件。
3. 在 face_compare.py 实现 compare_faces，并同步 provider_metadata。provider_metadata 只返回 connected、face_model、score_scale，不返回密钥或地址。
4. 本地提取器可使用已有 compare_batch_with_extractor，实现原图复用与换位配对。若要接入批量提取入口，须明确修改 check_real 的调用方式并补测试；当前默认仍调用逐对 compare_faces。
5. 适配器须遵守超时、重试和预算；明确原图／候选无脸、多脸及单张失败的政策。当前仍保持整轮失败，不能偷偷放行剩余候选。
6. 原图 A／B 稳定对应，两个分数独立；用授权真实回归集标定阈值与效果。
